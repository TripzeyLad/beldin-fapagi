# Permission boundary

OBSERVE: `health_snapshot` returns a cached read-only snapshot. SAFE_ACTION: `reload_config` reserved but disabled. SYSTEM_CHANGE: reserved and disabled. BLOCKED: shell always denied. No client-supplied executable, script, path, URL or command is accepted. Dispatch accepts exactly `{action: string, input: object}`. All actions use bearer authentication.

No mutating action exists, so repeated observation requests are safe and no mutation replay cache is necessary yet. Do not enable mutation by toggling the metadata flag: a separately implemented handler and tests are mandatory.

Required future SYSTEM_CHANGE handshake design (not executable in v1): authenticated proposal contains exact allowlisted action, canonical validated arguments and a unique request ID. Server creates a cryptographically random challenge bound to that proposal, requesting principal, current configuration generation and a 60-second expiry. A separate local human approval step—not the same model credential—approves that digest. Dispatch atomically consumes approval and request ID before execution, with a durable bounded journal to reject duplicates across restart. Expired, changed, replayed or unapproved proposals fail closed. Crash recovery reports indeterminate completion and never blindly retries. BLOCKED is never overridable by a challenge. No approval endpoints are exposed now.

## Human-approval boundary (implemented 2026-09-20)
Confirming any consequential action (`/v2/actions` op=confirm, chat "yes" for desktop actions, Control Center confirm) now requires the header `X-Beldin-Approval` matching a SEPARATE `approval_token` (config.local.json or BELDIN_APPROVAL_TOKEN; 32+ chars, must differ from the client token). The ordinary bearer token can propose and cancel but can never confirm, and the words "yes"/"confirm" alone never approve. With no approval_token configured, confirmations are refused (fail closed). Give the approval token only to the human-facing client (Surface voice terminal, after live speech, as BELDIN_APPROVAL_TOKEN). `setup_local.py` generates it. Each confirmation is first written to the durable hash-chained journal `audit/actions.jsonl` (beldin/audit.py); if that write fails the action is not executed. Backups, notes and snapshots use unique, exclusive-create names so same-second operations cannot overwrite each other.

## Coding acceptance (implemented 2026-09-20)
`/v2/coding` create accepts optional `requirements` (list of statements) and `constraints` (`forbidden_paths`, `max_files`, `required_tests`). `finish` must supply `evidence` {"R1":{"files":[...],"tests":[...]}}; files must be in the proposed change and tests must appear as passed in the validation run for that exact digest. Incomplete acceptance blocks approval-ready status and `approve`. Tasks with no declared requirements are labelled `acceptance: unmapped` rather than treated as verified. Any edit resets acceptance.
